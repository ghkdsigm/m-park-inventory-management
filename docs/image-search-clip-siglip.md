# 이미지 유사검색 — CLIP/SigLIP 임베딩 방식 전환 계획

> 모바일 "제품 찾아보기"(사진 촬영 → 유사 등록제품 리스트)를 **GPT 비전 API 대신 자체 호스팅 임베딩 모델**로 전환하기 위한 설계/검토 문서.
> 지금은 코드 변경 없이 **방향과 아키텍처만** 정리한 것. 실제 구현은 추후.

---

## 1. 배경

- **현재 방식**: `POST /api/chat/find-similar` 가 촬영 사진 + SKU 텍스트 카탈로그를 **GPT-4o(vision)** 에 보내, 유사한 SKU 후보를 구조화(tool call)로 받아옴.
- **한계**: OpenAI API **호출당 과금**(사용량 기반). 사용자가 많지 않은 사내 도구엔 비용 대비 부담.
- **목표**: **무료 오픈웨이트 모델**을 **AWS EC2에 이미지 분석 전용 API로 배포**해 GPT 자리를 대체. 저사용·경량 지향.

---

## 2. 대안 비교 (요약)

| 방식 | 무료 | 경량 | 이 용도 적합도 | 비고 |
|---|---|---|---|---|
| **CLIP/SigLIP 임베딩 유사도** | ✅ | ✅ | ⭐⭐⭐ | 이미지↔이미지 검색의 정석. **채택 방향** |
| 오픈소스 경량 VLM (Moondream2, Florence-2, Qwen2.5-VL 3B) | ✅ | △~✅ | ⭐⭐ | 대화형 인식 원할 때 |
| 무료 티어 호스팅 API (Gemini Flash, Groq) | 무료한도 | - | ⭐⭐ | 자체호스팅 싫을 때 |

---

## 3. 채택 방향: CLIP / SigLIP 임베딩 유사도

### 3.1 핵심 개념 — "모델 1개 + 간단한 계산"

- **CLIP**(OpenAI) / **SigLIP**(Google) 은 **임베딩(인코더) 모델**이다. 생성형 LLM이 아님.
  - 하는 일: **이미지 → 벡터(숫자 배열, 예: 512~1152차원)**
  - 텍스트도 같은 공간의 벡터로 변환 가능(이미지↔텍스트 검색도 됨)
- **유사도는 모델이 아니라 수학**: 두 벡터의 **코사인 유사도**(정규화 후 내적)로 가까운 정도를 계산.

```
[모델(CLIP/SigLIP)]  사진 → 벡터
        │
        ▼
[계산(코사인 유사도)]  촬영 벡터  vs  미리 저장된 카탈로그 상품 벡터들
        │
        ▼
   가장 가까운 상위 N개 SKU 반환
```

> SigLIP 가 보통 CLIP 보다 검색 정확도가 좋음(최신). 둘 다 무료 오픈웨이트.

### 3.2 전체 아키텍처

```
[상품/SKU 이미지 등록·수정]                 [모바일 촬영]
        │                                        │
        ▼                                        ▼
  EC2 임베딩 API (CLIP/SigLIP)           EC2 임베딩 API (동일 모델)
        │  벡터 생성(1회)                        │  벡터 생성(요청당 1장)
        ▼                                        ▼
  DB 에 SKU별 벡터 저장  ───────►  백엔드: 저장된 벡터들과 코사인 유사도 비교
  (pgvector / 배열 컬럼)                          │
                                                 ▼
                                       상위 N개 SKU + 위치정보 → 프론트 리스트
```

## 4. 정확도 기대치

정확한 %는 **실제 카탈로그로 테스트 필수**. 카탈로그가 얼마나 시각적으로 구별되는지에 크게 좌우됨.

| 상황 | 대략 정확도 |
|---|---|
| 카테고리 인식 ("이건 노트북이다") | **~95%+** |
| 서로 다른 종류 사이 정확한 SKU (노트북 vs 병 vs 케이블) | Top-1 ~80~90% |
| **비슷한 변형끼리** 정확한 SKU (같은 생수 500ml vs 2L, 라벨만 다른 것) | Top-1 ~55~75%, **Top-5~10 recall ~85~95%** |

### 4.1 GPT 대비 트레이드오프 (중요)

- **GPT-4o**: 사진 속 **글자(모델명·브랜드·라벨)를 읽고(OCR) 추론** → 겉모습 거의 같은 걸 잘 구분. 그래서 정확해 보임.
- **CLIP/SigLIP**: **전체적인 생김새(형태·색·질감)** 로 비교 → 카테고리는 완벽하지만 **미세한 텍스트 차이는 약함**.

### 4.2 실용성 판단

- 지금 UI가 **후보를 리스트로 보여주고 사용자가 선택**하는 방식 → 중요한 지표는 **Top-N recall** → **충분히 실용적**("정답이 후보 안에 거의 있음").
- **정확도 더 필요하면**:
  1. **CLIP + 가벼운 OCR** 조합 (라벨 글자 읽어 미세구분 보조) → GPT급 근접, 무료 자체호스팅 정석
  2. **본인 상품사진으로 파인튜닝** → 미세구분 크게 향상(작업 필요)
  3. 후보 넉넉히(Top-10), 촬영 물체 크롭, 일관된 촬영 환경
- **주의**: 기준 이미지(깔끔한 상품컷) vs 촬영 환경(창고에서 지저분) 차이가 크면 정확도 하락 → 크롭/일관 촬영 도움.

## 5. EC2 배포 (t3 / CPU, GPU 없음)

CPU로 구동 가능. 인스턴스 크기가 관건.

| 인스턴스 | RAM | 가능성 |
|---|---|---|
| t3.micro | 1GB | ❌ 빠듯(모델+PyTorch OOM 위험) |
| t3.small | 2GB | △ ONNX/양자화 + 작은 모델이면 가능 |
| **t3.medium** | **4GB** | ✅ **ViT-B/32 무난, 권장 최소** |
| t3.large | 8GB | ✅ SigLIP-L 등 여유 |

- **속도**: CPU에서 이미지 1장 임베딩 ≈ **0.2~1초**(ViT-B/32), 큰 모델은 1~3초. 현재 UX엔 충분.
- **버스터블(t3)**: 저사용·간헐 호출이면 오히려 잘 맞음(가끔 확 쓰고 쉼). 지속 부하면 CPU 크레딧 소진 후 느려짐.
- **필수 최적화**:
  1. **카탈로그 벡터는 미리 계산(offline)** → 런타임엔 촬영 사진 1장만 임베딩
  2. **ONNX Runtime + int8 양자화** → CPU에서 2~4배 빠르고 RAM 절약(→ t3.small 도 노려볼 만)
- **비용 절감**: 안 쓸 때 인스턴스 정지(근무시간만 가동 등). GPU(g4dn)는 이 용도·사용량엔 과함.
- **서빙 스택 예**: FastAPI + `transformers`/`sentence-transformers` (또는 ONNX Runtime) → "이미지 넣으면 벡터 주는" 엔드포인트 1개.

## 6. 자동 임베딩 설계 (SKU/상품 이미지 등록 시)

**검색할 때마다 재분석하지 않고, 등록 시점에 벡터를 만들어 저장**하는 것이 핵심.

### 6.1 임베딩 생성 트리거
- 이미지 **업로드/등록 시** → 벡터 생성 → DB 저장
- 이미지 **교체/수정 시** → 벡터 재계산
- 이미지 **삭제 시** → 벡터 제거
- **기존 SKU 전체** → 최초 1회 **백필(batch) 스크립트**로 채움

### 6.2 저장
- SKU 테이블에 **벡터 컬럼**(JSON/배열) 추가, 또는 별도 임베딩 테이블, 또는 **pgvector**(Postgres 확장 — 최근접 검색을 DB가 처리)
- 벡터는 **정규화(unit length)** 해서 저장 → 코사인 = 내적이라 계산 단순

### 6.3 런타임 검색
- 촬영 사진 **1장만** EC2로 임베딩 → 저장된 카탈로그 벡터와 유사도 비교 → 상위 N개
- 상품 수백~수천이면 메모리 브루트포스로 즉시. 많아지면 pgvector / FAISS.

### 6.4 ⚠️ 모델 일관성 (반드시)
- **카탈로그 임베딩과 촬영 임베딩은 같은 모델·같은 버전**으로 뽑아야 비교 가능. (CLIP 벡터와 SigLIP 벡터 혼용 불가)
- **모델 변경/업그레이드 시 → 카탈로그 전체 재임베딩** 필요. → 모델 버전 고정 관리 중요.
- 업로드 UX 지연 싫으면 **비동기(큐/백그라운드 잡)** 로 임베딩 처리.

## 7. 전환 시 구현 체크리스트

- [ ] EC2에 CLIP/SigLIP 임베딩 API 배포 (t3.medium~, ONNX/양자화 권장)
- [ ] DB에 SKU 임베딩 저장소 마련 (pgvector 또는 배열 컬럼, 정규화 저장)
- [ ] 상품/SKU 이미지 **업로드·수정·삭제 훅**에 임베딩 생성/갱신/삭제 연결 (비동기 권장)
- [ ] 기존 이미지 **백필 스크립트** 1회 실행
- [ ] 백엔드 `find-similar`를 GPT 호출 대신 **임베딩 검색**으로 교체 (응답 형식은 현행 유지: `{skuId, code, productName, imageUrl, locations, totalQty, ...}`)
- [ ] (선택) 정확도 보완: **경량 OCR** 결합 또는 상품사진 파인튜닝
- [ ] 실제 카탈로그로 **Top-N recall 측정** 후 N값·모델 크기 결정
- [ ] 모델 버전 고정 + 변경 시 재임베딩 운영 규칙 문서화

## 9. 한 줄 요약

- **CLIP/SigLIP = "이미지→벡터" 모델**, **유사도 = 그 벡터로 하는 계산**. 이미지 검색의 정석이며 무료·경량.
- **t3.medium(4GB)** 부터 CPU 구동 안정적, ONNX/양자화로 더 가볍게.
- **이미지 등록 시 자동 임베딩 + 기존분 백필**, **같은 모델로 일관성 유지**가 핵심 아키텍처.
- 리스트-선택 UX라 **Top-N recall 기준 충분히 실용적**, 미세구분은 **OCR 결합/파인튜닝**으로 보완.
